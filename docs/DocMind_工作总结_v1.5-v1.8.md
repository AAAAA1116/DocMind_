## 一、一句话结论

**切分层与精排层各拿到一次「精确修复、零副作用」的收益，问题被推到了检索层。**
结构切分把切点对齐率从 21.1% 拉到 100.0%，精排（改托管 API 后）把 Golden Set 从
16/18 推到 **17/18**；两次改动都是「唯一变化的那一条由失败转通过，其余全不动」。
剩下一题（q26）实测**不是系统缺陷，是用例判据歧义**。

## 四、v1.5 —— 结构切分

### 4.1 为什么改

原来的切分是「定长 500 + 80 重叠」，对条款体文档是错的工具。实测 7 份制度 PDF：

- 原子条款 **1005 条**，平均 177 字/条，`p50 = 117`；**42.3% 的条款不足 100 字**
- 现状下**切点对齐率只有 21.1%**（定长 92/436）—— 大量条款被拦腰切断
- 决定性对照：q10 金诚信内控**八要素**全在 427 字的一段里，定长切分把它切成
  「6/8 + 2/8」两块，检索只捞回半截，模型只能答前三项

### 4.2 定死的参数（一个主逻辑 + 两个补丁）

| 项 | 取值 | 说明 |
|---|---|---|
| 切点 | `第X条` | 章标记 `第X章` 只负责 flush，内容仍走通用逻辑 |
| 上限 | 480 字 | 由 token 实测推出，见 4.3 |
| 补丁 A | 超长条款二次切，**每个续块补条款头** | 宽度按 `chunk_size - len(条款头)` 算，否则续块带前缀会超上限 |
| 补丁 B | 相邻短条款贪心合并 | **禁止跨章** |
| 重叠 | 0 | 切点即语义边界，重叠纯属冗余（还会和正确答案抢 `TOP_K` 名额） |
| 自动退回 | 条款数 < 5（`_MIN_ARTICLES`） | 无条款结构的 demo txt/md 自动走原定长逻辑 |

### 4.3 480 这个数字的来源（不是随手取整）

`bge-small-zh-v1.5` 的 `model_max_length = 512`。实测压缩比 **0.956 token/字**：

```
400 字 = 382 token    440 字 = 420 token    480 字 = 459 token
500 字 = 478 token    520 字 = 497 token    560 字 = 535 token  ← 越界
```

扣掉 10% 余量取 480。**越界是静默截断** —— 超出 512 token 的部分根本不进向量，
不报错、不打日志，只表现为「这段内容怎么都搜不到」。
（另注：`config.py` 里 `RERANK_MAX_LENGTH` 那段旧的「500 字 → 378 token」注释是错的，
两者 tokenizer 不同，已在注释里标注。）

| 切点对齐率 | 21.1%（92/436） | **100.0%（523/523）** | +78.9pt |
| 块长 p50 | 485 | 390 | — |

| 索引展开率 | 1.20x | **0.96x** | 重叠没了，索引总体积反而降 |
| q10 八要素 | 切散成 6/8 + 2/8 | **8/8 同块** | 修复 |

**ragas（同 31 条、同 config，唯一变量 = 切分）**

| 忠实度 | 0.9622 | 0.9663 | +0.004 |

| **上下文召回** | 0.8571 | **0.9345** | **+0.077** |
| **上下文精度** | 0.6064 | **0.7077** | **+0.101** |

### 4.5 期间试过又回滚的：prompt 加 5 条规则

从失败用例提炼了 5 条规则写进 `SYSTEM_PROMPT_TEMPLATE`（枚举列全 / 跨司分列 /
不得编造 / 主体不张冠李戴 / 资料不足则拒答），同索引同 config 跑 `v1.5-prompt`：

| 指标 | 旧 prompt | 新 prompt | 变化 |
|---|---|---|---|
| 答案相关性 | 0.8974 | 0.8164 | **−0.081** |
| 误拒率 | 7.1% | 14.3% | **+7.2pt（翻倍）** |
| 平均耗时 | 1347 ms | 2189 ms | **+62%** |
| 上下文召回 | 0.9345 | 0.9345 | 0（符合预期） |
| 判据整条通过 | 16/18 | 16/18 | 0 |

**结论：回滚**（`rag_chain.py` 已复原，结果文件保留在 `eval/results/v1.5-prompt*.json`）。

最有价值的发现是**机制**：规则 2「逐家分别给出」对**单公司问题也套用分列格式**，
于是 q06 变成「北辰：未找到 / 新宝：未找到 / 龙旗：52,220.2644 万元」——
它没有改善检索，只是**把「检索失败」翻译成了另一种失败形态**。
⇒ 失败主因不在 prompt 层时，从失败用例提炼的规则不但无效，还会引入新偏差。

## 五、v1.6 / v1.7 —— 界面

### 5.1 v1.6：精简为「上传 + 提问」

设计原则：**「简易」不等于「删功能」，是把不常用的收起来。**

- 侧栏「当前参数 / 敏感操作 / 最近日志」三块 → 合并进**一个**「高级」折叠面板（默认折叠）
- 新增勾选框「在依据里显示检索诊断」（`session_state.show_diag`，默认关）：
  `render_sources()` 默认只显示「**依据 N：文件名**」，分数 / 名次 / 块号 /
  「哪一路召回的」只在开启时显示
- 主区 caption 去掉技术信息，空状态改口语化引导
- 删除：阈值那段长解释（`THRESHOLD = 0` 时本来就是死分支，永不执行）

### 5.2 v1.7：修「找不到问答入口」

**症状**：用户反馈「只有知识库和已入库文件，没看见问答的地方」。

**诊断**（结论与最初猜测完全不同）：代码里 `st.chat_input` 一直都在，AppTest 零异常。
抓真实渲染后的 DOM 才发现，`stChatInputTextArea` 在 **y = 801、视口高 900** ——
输入框**确实存在且可见，但贴在视口最底部**，而主区上半是大片留白，
第一次打开的人根本不会认为那条几乎无色的灰线是个输入框。

**改动**（业务逻辑零改动）：
1. 给 `[data-testid="stChatInput"]` 加蓝色边框 + 阴影 + 圆角。选择器只用 `data-testid`
   （Streamlit 为自动化测试保留的稳定钩子），**不碰 `st-emotion-cache-*` 那种每次构建
   都会变的哈希类名**
2. 新增只在 `messages` 为空时显示的「怎么用」引导卡片
3. `placeholder` 改为「在这里输入你的问题，按回车发送」

**自己犯的错（已修）**：引导卡片里原来写「试试问三家公司的注册资本分别是多少」——
那**正是评测集里答不出的 q06**。界面亲自推荐一个会失败的问题，等于自己拆自己的台。
改成只教提问方式、不承诺任何具体答案。

**验证方式不是「看端口通不通」**：AppTest 无异常 + CDP 真实浏览器**输入并提交**，
端到端拿到回答与依据。

## 六、v1.8 —— 精排改托管 API

### 6.1 本地精排为什么被否掉

v1.4 的结论「精排不值」（精度涨但耗时 23 倍）**只证明了本地精排不可用**，不是算法没用：

- 本机只有 8GB 内存，跑前可用 1.87GB；bge-reranker（XLM-R-large，568M 参数）
  FP32 权重就 2.3GB
- 池 50 实测 **177 秒/问**，池 100 实测 **344 秒/问**
- 池 100 跑第二题时内存爆 → Windows 疯狂换页 → **卡死 2 小时 19 分，日志连着 132 分钟无输出**
- ⇒ **8GB 机器上跑 CPU 精排不只是「慢」，是会拖死整机。**

### 6.2 选托管 API 的过程（含一次失败）

| 路线 | 结果 |
|---|---|
| 阿里云百炼 `gte-rerank-v2` | ❌ 账户欠费，`HTTP 400 Arrearage`，且 `qwen-turbo` / `qwen-max` 同样报错 ⇒ 整个百炼账户停摆 |
| 硅基流动 `BAAI/bge-reranker-v2-m3` | ✅ **该平台免费模型**，100 候选 1.4~2.0 秒，零本地内存占用 |

**教训**：那次欠费导致的 18 条全灭是**假成绩**（0/18 只代表「没让进门」）。
此后脚本加了 **API 预检**（1 问 1 文档，失败即退出），不再跑完整批才发现券没了。

**两家返回结构不同，换 URL 不行**：硅基流动是顶层 `results`，百炼是 `output.results` ——
`core/reranker.py` 里做了适配。分数尺度也不可跨模型比较（同一块：本地 0.988 vs 百炼 0.2449）。

### 6.3 候选池大小的反直觉结论

池子**不是越大越好**。q06 的三个答案块实测名次：

| 池 | 北辰 | 龙旗 | 新宝 | `TOP_K=12` 时 |
|---|---|---|---|---|
| 100 | #3 | #7 | #10 | **3/3 ✅** |
| 200 | #3 | #9 | #12 | 3/3（卡线） |
| 300 | #3 | #10 | #13 | 2/3 |

⇒ **召回任务的池子大是纯赚，排序任务的机会和竞争者一起增加**，甜点是 **池 100~200 + `TOP_K` 12**。

### 6.4 落地改动与回归

**代码**：`core/reranker.py` 新增 `_APIReranker`（本地实现完整保留作 fallback）、
`provider_info()`；`config.py` 开关与参数（`RERANK_ENABLED` True、候选池 100、`TOP_K` 12）；
`app.py` 预热按后端分流；`.env.example` 补 key 说明。

**降级路径实测**：key 置空 → 打一行日志、退回 RRF 排序，**答案照出、不崩**。

**18 条 Golden Set 回归**（脚本复刻 + 真实 `rag_chain.answer()` 双跑一致）：

| 指标 | 基线（池 10 + 无精排 + K=8） | v1.8（池 100 + API 精排 + K=12） |
|---|---|---|
| 整条通过 | 16/18 (88.9%) | **17/18 (94.4%)** |
| 检索短语命中率 | 0.85 | **0.95** |
| 要点覆盖率 | 0.9412 | **0.9804** |
| 违例 | 0 | 0 |
| 负例拒答 | 3/3 | 3/3 |
| 耗时/条 | 1.35 s | 3.38 s（去冷启 2.52 s） |

**q06 由 FAIL 转 PASS（要点 1/3 → 3/3），其余 17 条零退化。**

### 6.5 顺带修正的一处「摘要说假话」

`config.summary()` 原来打印「各取 `HYBRID_PER_SOURCE` 个」（= 10），而真实召回深度是
`max(HYBRID_PER_SOURCE, k)`，其中 `k = max(RERANK_CANDIDATES, TOP_K) = 100` ——
**显示 10、实际取 100**。这会让人误以为调 `HYBRID_PER_SOURCE` 有效（真去调，看不到任何变化）。
已改为打印真实深度并注明它由候选池决定。

## 七、q26 的定性：不是系统缺陷，是用例判据歧义

这一条花的时间最多，结论也最明确：

1. **池这一层就挡**：正解块 BM25 全库排 124，而 `per_source = 100` → 该路被截断，
   只剩向量一路的分 `1/(60+59) = 0.008403`，两路都命中的块 ≥ 0.0125 直接压过它
   ⇒ **实测 `k = 100` 时它根本不在池内**
2. **精排这一层也挡**：即使进池，两个不同厂商的模型给出**一致判断**——
   本地 bge 给 0.0735、百炼 gte 给 0.1576，而干扰块（长川第八十条）是 0.395 / 0.2004。
   两个模型跨题判别力都正常（q26 池内 q06 的块排 #141~#201），
   ⇒ **这块跟问题不相关**，不是精排失灵
3. **判据这一层最关键**：判据 `must_include` 抄的是「（七）董事长或者经理无法履行职责」，
   **该条款不含「三个月」**；而用户问的「生病三个月」对应的是**排除条款**
   （「除董事长或者经理外…三个月以上」）—— **两者结论相反**。
   ⇒ 用户问法与该判据指向的是**不同条款**，这条用例的 `must_include` 本身有歧义

**已修正的两个认知**：
- 早期记的「原文根本没有『三个月』」**不准确** —— 文档里有「三个月以上」，只是在排除条款里
- 早期记的「q26 融合排名 65」**不适用于池 100**（那是 k=200 时的数字）

其余 13 条是 v1 独有题，裁判自动跳过 —— 不是错误。

**判据里的三个坑（写数据时会再踩）**：
1. **判据必须从语料里抄，不能从人写的参考答案里抄** —— v1 的数据集分句可达率只有 42.6%，
   根因是 `ground_truth` 是改写过的概括语（把「公司的注册资本」写成「北辰实业的注册资本」、
   自加「五个」这种数目字）。字面匹配对「多一个字」零容忍
2. **归一化必做**：索引里的块是硬换行切过的，`[[Pn]]` 页码标记还会嵌在句子中间（君逸第四十五条）。
   不做「去空白 + 去 markdown + 去页码标记」，判据会成片假失败
3. `must_not_include` **优先用「结论性错误」**（如「不需要披露」），不要用「干扰源词组本身」——
   后者在文档里真实存在，会误伤严谨的对比型答案

## 十、环境坑（这台机器上踩过的，按重要性排）

1. **8GB 内存的硬约束**：跑任何本地模型前先看可用内存。本地 reranker 池 100 会卡死整机
   （实测 2 小时 19 分无输出）。**这不是「慢」，是拖死。**
2. **改 `config.py` 必须重启进程**：Streamlit 的 file watcher 只重跑脚本，不刷
   `sys.modules` 缓存 —— 版本号会一直显示旧值
3. **`taskkill /F` 杀 Streamlit 后立刻重启**，首个请求可能撞上 Chroma 连接未释放，
   报 `Could not connect to a Chroma server`（主区空白 + Stop 亮）。**重试即恢复**，
   先看服务端日志再怀疑代码
4. **两个 Streamlit 实例会抢同一份 chroma 索引**（8502 主区渲染不出来）。验证新代码不要开第二端口
5. **长脚本（>5 min）输出会被吞 + 进程 SIGTERM** → 必须 `python -u` + 重定向到文件再读，
   否则看到的是空输出，误以为脚本没跑
6. **Git Bash 里 `ls` / `head` / `tail` / `dirname` 会 `command not found`**（PATH 丢失），
   需要显式补 PATH
7. **`wmic` 被安全策略拉黑** → 查进程改用 `netstat -ano` + `taskkill /PID`
8. **Chrome `--screenshot` / `--dump-dom` 对 Streamlit 不可靠**（websocket 推送，virtual time
   会截到骨架屏；`--dump-dom` 同一页面两次抓取结果不一致）。**必须用 CDP**：
   navigate → sleep → `Page.captureScreenshot`
9. **`AppTest.from_file()` 的相对路径按「调用它的脚本」所在目录解析**，不是 cwd ——
   验证脚本放临时区时必须传绝对路径
10. **写 git patch 文件时注意行尾**：Python 的 `write_text()` 在 Windows 上会把 `\n`
    转成 `\r\n`，patch 上下文行多出 `\r` 会导致 `git apply` 失败。要用 `newline=''`
